# Data Model: Coordinate Get-Together

## User

A registered person. This is the Django authentication user, with email as the unique login identifier.

| Field | Type | Rules |
|---|---|---|
| id | integer | Primary key |
| email | string | Required, unique, case-insensitive, valid email address |
| password | string | Required, stored only as a Django password hash |
| display_name (It would be better to change the name of this field to `name`.) | string | Required, 1–150 characters after trimming whitespace |
| is_active | boolean | Django account state; inactive users cannot authenticate |

Relationships:

- A user organizes zero or more events.
- A user has zero or more participations.
- A user reaches authored suggestions and agreements through participations. Authorship and agreement are not stored directly on the user.
- A user has at most one agreement per event.

Identity shown in the interface is `display_name`, with email retained as the account identifier.

## Event

A get-together owned by one organizer.

| Field | Type | Rules |
|---|---|---|
| id | integer | Primary key |
| organizer | foreign key to User | Required, immutable after creation |
| title | string | Required, 1–200 characters after trimming whitespace |
| details | text | Optional, maximum 5,000 characters |
| invite_token | string | Required, unique, unguessable, generated by the server |
| status | enum | `active` or `finalized`; new events start as `active` |
| final_suggestion | foreign key to Suggestion | Null while active; required when finalized |
| created_at | timestamp | Set when created |

Relationships:

- An event has one or more participations. Creation also creates the organizer's participation.
- An event has zero or more suggestions.
- An event has zero or more agreements through its suggestions.

State transitions:

1. `active`: participants may join through the invitation link and may change suggestions and agreements, subject to authorship and organizer rules.
2. `finalized`: joining, suggestion changes, and agreement changes are rejected. The transition requires the organizer, at least one agreement made by someone other than the organizer, and exactly one selected suggestion that is tied for the highest agreement count. The organizer's own agreement does not satisfy the agreement requirement. It is irreversible in this release.

The invitation URL is `/events/<invite_token>/`. The token is not a sequential identifier.

## Participation

The authenticated association between one user and one event.

| Field | Type | Rules |
|---|---|---|
| id | integer | Primary key |
| event | foreign key to Event | Required |
| user | foreign key to User | Required |
| joined_at | timestamp | Set when the participation is created |

Rules:

- A user has at most one participation in an event.
- The organizer's participation is created with the event.
- A signed-in user opening a valid invitation link joins only while the event is `active`.
- After finalization, an existing participation grants read access, but the invitation link creates no new participation.

## Suggestion

A complete proposed option for when and where one event can happen, such as a specific date and time at a specific place. It is not an arbitrary free-text idea. The event's optional `details` remain unstructured notes; the selectable time and place belong only to suggestions.

| Field | Type | Rules |
|---|---|---|
| id | integer | Primary key |
| event | foreign key to Event | Required and immutable |
| author | foreign key to Participation | Required and immutable; `author.event` must equal `event` |
| proposed_at | timezone-aware datetime | Required. One `DateTimeField` represents both the proposed date and time |
| location | string | Required, 1–200 characters after trimming whitespace |
| description | text | Optional, 1–2,000 characters after trimming whitespace |
| created_at | timestamp | Set when created |
| updated_at | timestamp | Updated when `proposed_at` or `location` changes |

`author` references `Participation`, not `User`. A suggestion belongs to one event membership, and each user has at most one participation in an event. The participation foreign key plus the same-event constraint guarantees that only a member of that event can author it. A direct user foreign key cannot express that constraint. The author shown in the interface is still that participation's user, so attribution is unchanged. Authorship is immutable, and participant removal is outside this release, so the reference is neither reassigned nor emptied.

The event foreign key remains even though it can be reached through `author`. Suggestions are children of an event, including the event's final suggestion, and the duplicate reference makes a mismatched author detectable.

No description, end time, duration, or map coordinates are stored. The product needs the time and place being compared, and commenting is outside this release. Both `proposed_at` and `location` are required: an option missing either one cannot answer which time and place works. The event itself still requires only a title; its date, time, and location are not separate event fields. No rule requires the proposed time to be in the future.

Rules:

- Suggestions can be created or edited only while the event is `active`.
- The user represented by `author` may edit or delete the suggestion.
- The organizer may delete any suggestion in the event.
- The organizer may edit a suggestion only when the organizer's participation is its `author`.
- A suggestion that is the event's final suggestion cannot be deleted.
- Creating a suggestion does not create, delete, or move any agreement.
- Editing `proposed_at` or `location` does not clear or move the suggestion's agreements. Existing agreements stay with that suggestion until each participant agrees to a different suggestion or the suggestion is deleted.
- Deleting a suggestion deletes its agreements. If a deletion leaves no agreement made by someone other than the organizer, the event remains active and cannot be finalized until such an agreement exists. The organizer's own agreement does not satisfy this requirement.

Agreement count is the number of related Agreement rows. It is not stored separately. Finalization still compares those counts and does not rank suggestions by time or location.

## Agreement

One participant's support for one suggestion in an event.

| Field | Type | Rules |
|---|---|---|
| id | integer | Primary key |
| event | foreign key to Event | Required and immutable |
| suggestion | foreign key to Suggestion | Required; its event must equal `event` |
| participant | foreign key to Participation | Required and immutable; the participation's event must equal `event` |
| created_at | timestamp | Set when created |
| updated_at | timestamp | Updated when the agreement moves |

Rules:

- A participation has at most one agreement per event. This preserves one agreement per user per event because participation is unique per user and event.
- The identity displayed for an agreement is the participation's user.
- `participant.event`, `event`, and `suggestion.event` must all match. The suggestion's author is also a participation in that same event.
- Agreeing to another suggestion in the same active event updates that row's suggestion; it does not create a second agreement.
- A new or edited suggestion does not invalidate existing agreements. A participant replaces an earlier agreement only by agreeing to a different suggestion.
- A participant may move their agreement while the event is `active`.
- Agreement changes are rejected when the event is `finalized`.
- The replacement is performed in a transaction so concurrent requests cannot leave the same participation with two agreements.

## Validation and integrity

- Event titles, user names, and suggestion locations are trimmed before validation. Empty results are rejected with a field-specific message.
- A suggestion requires both `proposed_at` and a non-empty `location`. A blank location or missing date and time is rejected, and no suggestion is created.
- Duplicate email addresses are rejected with a message directing the person to sign in.
- Database uniqueness enforces one email per user, one invitation token per event, one participation per user and event, and one agreement per participation and event.
- Constraints enforce `suggestion.author.event == suggestion.event` and `agreement.participant.event == agreement.event == agreement.suggestion.event`.
- Finalization locks the event row, recounts agreements, and rejects a selected suggestion that is not among the current highest-count suggestions.
- Invalid tokens and finalized events viewed by non-participants produce the same unavailable-event response, without event content.
